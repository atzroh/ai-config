# リファクタリング

挙動を変えずにコードの構造を改善するためのスキル。
進め方は「提案 → 承認 → 承認された項目だけ実施」の 3 段階。ユーザーは変更を把握したうえで選びたいので、提案の段階ではコードを一切変更しない。

```
依頼
 └─ 1. 対象と目的の確認
 └─ 2. 現状把握 (コード読解、テストの有無確認、既存テストの実行)
 └─ 3. 提案一覧を提示して停止          <- ここで返答を待つ
 └─ 4. 承認された項目を 1 つずつ実施    <- 1 項目ごとに返答を待つ
       変更 -> テスト実行 -> 結果報告
 └─ 5. 完了報告
```

## 1. 対象と目的の確認

対象 (ファイル、関数、ディレクトリ) が依頼から読み取れないときは、推測せずに質問する。
対象外のファイルには触れない。対象外で気になった点は、提案一覧の末尾に「範囲外」として挙げるだけにする。

## 2. 現状把握

- `git status` で作業ツリーの状態を確認する。未コミットの変更があれば、提案の冒頭で伝える。クリーンな状態から始めれば、項目ごとの差分を `git diff` で示せて、取り消しも容易になるため。
- 対象のコードと、その呼び出し元・呼び出し先を読む。公開されている関数名やシグネチャを変える提案では、影響範囲 (呼び出し箇所の数とファイル) を把握しておく。
- リポジトリ内の命名、構成、コメントの書き方を確認する。提案はこの既存の書き方に合わせる。独自の流儀を持ち込むと、かえって統一感が崩れるため。
- formatter / linter (ruff、eslint、prettier など) の設定があるか確認する。
- テストを探し、あれば実行してベースラインの結果を記録する。実行コマンドはリポジトリの設定 (`pyproject.toml`、`package.json`、`Makefile` など) から判断する。
- テストがない、または実行できない場合は、提案の冒頭でそのことを伝える。その場合、変更後の挙動は未検証になる。

## 3. 提案一覧

### 観点

まず次の 5 つの観点で探す。ユーザーが特に重視している観点なので、該当する箇所は漏らさず挙げる。

1. **粒度をそろえる**: 1 つの関数の中で、高レベルな処理の呼び出しと細かい処理 (文字列操作、ループの中身など) が混在していないか。同じ階層の処理は同じ抽象度にそろえる。
2. **モジュール化**: 1 つの関数・クラス・ファイルが複数の責務を持っていないか。責務ごとに関数、ファイル、モジュールへ分ける。
3. **コメントを簡潔に**: コードを言い換えただけのコメント、古くなったコメント、長すぎるコメントはないか。削るか、意図 (なぜそうするか) だけを短く残す。
4. **命名に統一感を持たせる**: 命名規則 (snake_case / camelCase)、動詞の選び方 (`get` / `fetch` / `load` の混在など)、略語、単数・複数がそろっているか。
5. **無駄なラップを削除する**: 引数をそのまま渡して呼ぶだけの関数、値を詰め替えるだけの変数、状態を持たないのにクラスにしているものなど、間接層を増やすだけのものはないか。

次に、以下の観点でも探す。

- **I/O とロジックの分離**: ファイル入出力、通信、表示などの副作用が、計算・判定の処理に混ざっていないか。分けるとロジック単体で読め、テストもしやすくなる。
- **マジックナンバー・文字列**: 意味の読み取れないリテラル (`0.08`、`"admin"` など) に名前を付けて定数にする。
- **フラグ引数・多すぎる引数**: bool 引数で処理を切り替える関数は分割を、引数が多すぎる関数はまとめ方を検討する。
- **既存の部品の活用**: 標準ライブラリやリポジトリ内のユーティリティを再実装している箇所を置き換える。
- **その他**: 重複、深いネスト (早期リターンで浅くする)、使われていないコード。

### 抽象化しすぎない

「モジュール化」と「無駄なラップの削除」は逆方向に働く。分割を進めすぎると、このスキル自身が新しい無駄なラップを生む。
切り出しを提案するのは、名前を付けることで読みやすくなる、責務が明確に分かれる、複数箇所から使われる、のいずれかに当てはまるときに限る。呼び出し元が 1 か所で、名前が中身の言い換えにしかならないなら切り出さない。

### 形式

次の形式で提示し、ここで止めて返答を待つ。

```markdown
作業ツリー: クリーン                        # 未コミットの変更があればファイル名を挙げる
テスト: `uv run pytest` (12 passed)        # なければ「テストなし。変更後の挙動は未検証になります」

1. [高] 粒度をそろえる — `src/report.py:20-58` `build_report`
   集計の呼び出しと日付の整形処理が混在 → 整形処理を `format_date` に切り出す
2. [中] 命名に統一感 — `src/report.py:12` `getTotal`
   他は snake_case → `get_total` に改名
   影響範囲: `src/api.py` など 3 ファイルから呼ばれている
3. [中] ...

他に 3 件 (定数化、ループの簡略化など)。必要なら出します。
範囲外: `src/utils.py` にも同様の重複があります (今回は変更しません)

実施する番号を教えてください。
```

- 優先度は 高 / 中 / 低。読みやすさや保守性への効果が大きく、リスクが小さいものほど高くする。
- 提示するのは効果の大きい順に **最大 5 件** とし、[低] は出さない。項目が多すぎるとユーザーが選びきれず、かえって判断の負担になるため。優先度を付け直して件数を保つのではなく、本当に効果の大きいものだけに絞る。
- 5 件に入らなかった項目は、末尾に「他に N 件 (定数化、書き方の簡略化など)。必要なら出します」と 1 行で触れるだけにする。
- 各項目は見出し行 + 「問題 → 改善案」の 1 行にする。影響範囲は、対象ファイルの外に及ぶとき (公開関数の改名など) だけ 1 行足す。理由は、改善案から自明でないときだけ短く添える。
- 1 項目 = 1 つの意図にする。まとめて頼まれても、個別に承認・却下できるようにするため。
- 移動 (ファイル分割、関数の移設) と中身の書き換えは別の項目にする。混ぜると差分が読みにくく、テストが失敗したときに原因を絞れないため。
- formatter による見た目だけの整形も、構造の変更とは別の項目にする。
- 依存関係がある項目 (例: 3 は 1 の後でないとできない) はその旨を書く。
- 挙動が変わる変更 (バグ修正、エラー処理の追加など) はリファクタではないので、提案に混ぜない。気づいた場合は「範囲外」に別扱いで書く。

## 4. 実施

承認された番号だけを、1 項目ずつ実施する。各項目で次を行う。

1. 変更する。既存の命名・構成・コメントの書き方に合わせる。
   名前を変えるときは、grep や LSP で参照をすべて洗い出す。文字列による参照 (設定ファイル、`getattr`、テンプレート、ドキュメントなど) は見落としやすいので、これも検索する。
2. formatter / linter があれば、変更したファイルに対して実行する。
3. テストを実行し、ベースラインと比較する。
4. 変更内容 (`git diff` の要点) とテスト結果を報告し、次の項目に進む前に返答を待つ。

テストが失敗したら、次へ進まずに原因を報告する。挙動を変えないことがリファクタの前提なので、失敗は変更の誤りを示している可能性が高い。
実施中に提案時の想定と違う点 (影響範囲が広い、など) が見つかったら、変更を進める前に伝えて判断を仰ぐ。

## 5. 完了報告

- 実施した項目の番号と変更の要点
- 実行したテストのコマンドと結果 (変更前 / 変更後)
- 実施しなかった項目、未検証の項目 (テストがない部分など)
